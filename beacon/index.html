An evaluation that every agent passes measures nothing. An evaluation no agent can pass measures nothing either. Beacon exists to find the narrow band in between, and to prove a task sits inside it before it's trusted with real results.

03
What's been built

Three pieces, one pipeline

A task design discipline, the engine that enforces it, and a real open-source contribution that came out of using it in anger.

Calibrated task design

Every task is written the way a maintainer files a real issue, then checked both ways: nothing a hidden test expects is left unsaid, and nothing the description promises is left untested. Difficulty is engineered, not assumed.

Target band: 10–40% solve rate

The Beacon engine

A full local replica of the evaluation pipeline — static checks, patch application, a four-run test matrix, flakiness repeats, an AI-assisted read of whether the description and the tests agree, and trial agent rollouts — run as many times as it takes, in a throwaway copy of the repo, with a live dashboard.

Every gate run free, before one paid check

Open-source contribution

Shipped into Agno, an open-source multi-agent framework: a way for a team of AI agents to stream their work so a reader can tell which agent spoke, which is still reasoning, and which just finished — without breaking any test the framework already relied on.

Shipped, not simulated

Teaching a team of agents to say who's talking

In Agno, an open-source framework several teams build multi-agent systems on, a team of AI agents streams its work over one channel. Before this contribution, every member's output was folded into one anonymous stream — a transcript with no names in it.

The fix gives every member of the team, and every nested sub-team, its own message thread, its own reasoning trace, and a small set of attribution events a frontend can key off: who started speaking, who called a tool, who finished. None of it was allowed to break the 126 tests already protecting that code path — it had to add 52 new, independently verified behaviors on top of them, with zero regressions.

It's a small feature by line count. It's a real one by the discipline behind it: it passed through the exact Beacon pipeline diagrammed above before it was ever treated as done.

Why compute, specifically

From one GPU to a shared allocation

The Beacon engine's weakest link was never its logic. It was that a single consumer GPU can hold one small model in memory at a time — the moment a second agent tries to run alongside it, the system falls back to the processor, and the entire point of fast, free local iteration disappears.

An evaluation batch worth trusting needs a dozen or more agent attempts running where possible in parallel, not one attempt at a time. That's the gap a dedicated allocation on AU‑QUASAR's NVIDIA DGX H200 infrastructure closes.

Before

One model, one agent, one attempt at a time

8GB of consumer GPU memory, shared with every other process on the machine.

Now

A shared DGX H200 allocation, running agents in parallel

Enough headroom to run a full rollout batch at once, not a sample at a time.
